# 청산 점검 봇 (keeper)

대출 풀의 `poke`를 호출해서 포지션을 블라인드 청산 점검하는 Node 프로그램.
**가격이 떨어졌을 때만 바쁘게** 돌고, 평소에는 하루에 한 번만 점검한다.

## 규칙

```
시작할 때                            → 한 바퀴 점검, 기준 가격 = 현재 가격
1분마다 가격 조회 (조회라 가스 없음)
  · 가격이 기준보다 높으면            → 기준 가격을 올림
  · 가격 ≤ 기준 × (1 − 2%)           → 한 바퀴 점검, 기준 가격 = 현재 가격 (끝나면 바로 다시 확인)
마지막 바퀴 후 24시간이 지나면        → 한 바퀴 점검
```

**한 바퀴** = 등록된 포지션 수만큼 `poke(최대 3)`를 이어서 호출해, 모든 포지션을 한 번씩 점검하는 것.
포지션 10개면 트랜잭션 4건이다.

### 왜 이 규칙인가

포지션이 청산 대상이 되는 경로를 전부 따져 보면:

| 경로                     | 가능한가  | 봇의 대응                                           |
| ------------------------ | --------- | --------------------------------------------------- |
| 사용자가 너무 많이 빌림  | 불가      | 대출은 70% 한도 안에서만 승인된다                   |
| 사용자가 담보를 빼감     | 불가      | 빚이 0일 때만 반환된다                              |
| **가격 하락**            | 가능      | 1분마다 가격을 확인해 2% 이상 내려가면 바로 한 바퀴 |
| **이자 누적**            | 아주 느림 | 하루 0.027%p씩 오른다. 하루 한 바퀴로 충분          |
| 봇이 꺼진 동안 가격 하락 | 가능      | 다시 켜질 때 한 바퀴                                |

- **하락 기준 2%**: 기준을 X%로 잡으면 점검 사이에 빚 비율이 최대 `80% ÷ (1 − X)`까지 오른 뒤 잡힌다.
  2%면 81.6%로 청산선을 거의 넘지 않는다. 10%면 88.9%까지 올라가 손실 구간(약 95%)에 가까워진다.
- **기준 가격을 따라 올리는 이유**: 가격이 높을 때 한도까지 새로 빌린 사람은 높은 가격이 출발점이다.
- **정기 한 바퀴 24시간**: 이자로 청산선을 넘은 포지션도 하루 안에 잡힌다. 하루 늦어도 빚 비율은 80% → 약 80.03%라,
  손실선(100%)까지 20%p 여유가 그대로 남는다.
- **비용**: 60초마다 1건씩 점검하던 처음 방식보다 트랜잭션이 훨씬 적다 (포지션 10개, 하락 없는 날 기준 1,440건 → 4건).

처음(11/8)에는 사용자가 예치·대출·상환·반환을 할 때마다 다음 순번 포지션 2개를 함께 점검했다. 사용자가 적어
거래가 뜸하면 청산 대상이 오래 방치되는 문제가 있어서, 거래 중 점검을 없애고 이 봇으로 바꿨다
(사용자 거래도 가벼워졌다: borrow HCU 14.7M → 3.7M).

## 봇이 알 수 있는 것과 없는 것

|                                      | 봇이 아는가          |
| ------------------------------------ | -------------------- |
| 가격, 포지션 수, 다음에 점검할 순번  | 안다. 원래 공개 정보 |
| 점검한 포지션이 청산 대상이었는지    | **모른다**           |
| 청산이 일어났는지, 얼마나 청산됐는지 | **모른다**           |

- `poke`는 반환값이 없고, 남기는 이벤트도 `PositionChecked(user)`뿐이다.
- 청산 대상이면 컨트랙트가 **같은 트랜잭션 안에서** 암호문으로 청산까지 끝낸다. 봇은 아무것도 판단하지 않는다.
- 청산과 비청산은 이벤트 순서와 `gasUsed`까지 같다 (`hardhat/test/lendingPool.ts`에서 확인).
- 봇이 언제 점검할지는 공개된 가격과 시간만으로 정해지므로, 점검 시점에서 새는 정보도 없다.

`poke`는 누구나 호출할 수 있으니, 이 봇은 여러 개가 동시에 돌아도 된다
(공용 커서 `nextCheckIndex`를 이어서 쓰므로 같은 포지션을 겹쳐 점검하지 않는다).

## 준비

Node 22.18 이상 (TypeScript를 빌드 없이 바로 실행한다).

```bash
cd keeper
npm install
cp .env.example .env
```

`.env`에 **봇 전용 지갑**의 개인키를 넣는다 (`KEEPER_PRIVATE_KEY`). `.env`는 git에 올라가지 않는다.

- Sepolia 테스트 ETH만 있는 개발용 지갑을 새로 만들어 쓴다. `poke(1)` 한 건에 가스 약 160만이 든다.
- 대출 포지션이 있는 지갑으로 돌려도 된다. 다만 봇 키가 서버에 놓이므로, 자산이 없는 봇 전용 지갑을 권장한다.

## 실행

```bash
npm run dry-run   # 트랜잭션 없이 첫 트랜잭션만 시뮬레이션 (개인키 불필요)
npm run once      # 한 바퀴만 점검하고 끝냄
npm start         # 계속 실행 (Ctrl+C로 종료)
```

## 설정 (`.env`)

| 변수                 | 기본값                                       | 설명                                             |
| -------------------- | -------------------------------------------- | ------------------------------------------------ |
| `KEEPER_PRIVATE_KEY` | (필수, 드라이런 제외)                        | 봇 지갑 개인키                                   |
| `RPC_URL`            | 공개 노드                                    | Sepolia RPC                                      |
| `POOL_ADDRESS`       | `../frontend/src/contracts/deployments.json` | 대출 풀 주소. 봇 폴더만 서버에 올릴 때는 꼭 설정 |
| `PRICE_POLL_SECONDS` | 60                                           | 가격 확인 간격 (5~3600초)                        |
| `DROP_TRIGGER_BPS`   | 200 (= 2%)                                   | 한 바퀴를 도는 하락 기준 (1~5000 bps)            |
| `HEARTBEAT_HOURS`    | 24                                           | 정기 한 바퀴 간격 (1~168시간)                    |

## 동작 메모

- 한 바퀴는 겹쳐서 돌지 않는다. 도는 중에 가격이 더 떨어지면, 끝난 뒤 기다리지 않고 바로 확인해서 한 바퀴를 더 돈다.
- 보내기 전에 매번 시뮬레이션해서, 실패할 트랜잭션은 보내지 않는다.
- 한 바퀴가 중간에 실패하면 기준 가격을 바꾸지 않아서, 다음 확인 때 다시 한 바퀴를 돈다.
  연속 실패하면 확인 간격을 2배씩 늘린다 (최대 10배).
- 봇 지갑 잔고가 0.01 ETH 아래로 떨어지면 경고한다.
- 서버에서 계속 돌리려면 `pm2 start "npm start" --name keeper` 같은 프로세스 관리자를 쓴다.

## 탈중앙화 관점

봇은 편의를 위한 것이지, 신뢰해야 하는 주체가 아니다.

- 봇이 할 수 있는 건 "점검을 앞당기는 것"뿐이다. 결과를 보거나 바꿀 수 없다.
- 봇이 멈추거나 사라져도 누구나 `poke`를 부를 수 있다 (웹 화면의 "청산 점검" 버튼, `pool:poke` 태스크, 다른 봇).
  다만 아무도 부르지 않으면 점검이 멈춘다. 그래서 봇이 계속 돌도록 운영하는 것이 중요하다.
- 봇은 보상을 받지 않는다. 보상이 청산 여부에 따라 달라지면 청산 사실이 드러나기 때문이다.
  가스비는 봇 운영자가 낸다.
